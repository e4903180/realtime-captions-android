### 第 2 步的細節（開發紀錄）

**架構**
- `core/StreamingPipeline`：純 Kotlin，把串流辨識、VAD、說話者分群（和可選的降噪）接在一起，輸出既有的 `TranscriptEvent`。Android 和桌機共用同一份邏輯。
- `core/SpeakerClusterer`：每一行字幕算一個聲紋向量，和已知的人比較餘弦相似度；夠像就歸到同一人，否則開新的人（A、B、C…）。說話超過 1 秒時，未完成的字幕會先給暫定標籤。
- `:desktop`：在電腦上用同一條管線、以 100 毫秒為單位播放 wav，模擬真實時間，計算首次出字、句尾定稿延遲、錯字率（轉成台灣繁體後）和說話者正確率。
- App：`SherpaOnnxEngine`（顯示為「離線＋說話者」）、`ModelStore`（首次使用下載，ADR-012）、debug 版的「wav 當麥克風」。

**遇到的問題與解法**
1. 英文被切在字中間（"mil / k"、"Wo / uld"）、中文重複字（「需需要」）：Silero 內建分段在開始說話時要等 0.25 秒才判定，新的一句剛開始就被當成靜音而斷句。改用 Silero 原始機率自己計時，並要求文字穩定、斷句前補靜音（ADR-013）。修正後英文錯字率從約 20% 降到 0–1%。
2. 兩人的話黏在同一行：見 ADR-013。不用 VAD 斷句時說話者正確率只有 52–59%。
3. 簡繁轉換：模型輸出簡體字。opencc4j 的台灣轉換已包含台灣用語（軟件→軟體、視頻→影片、出租車→計程車、網絡→網路、信息→資訊）；少數字（裏、着、麪）另外補表轉成 裡、著、麵。
4. 模擬器實測（Pixel 8 API 35，用 wav 當麥克風）：第一次啟動時下載模型成功；中文三人對話 7 行全對、A/B/C 標籤全對；咖啡廳 5 dB 噪音版標籤也正確；英文對話全對。畫面上引擎按鈕太多會擠掉「A+」「清除」，改成兩列。
5. 取得資料時：AISHELL-1 官方鏡像沒有測試集的說話者檔，改用 parquet 鏡像，再用官方逐字稿比對找回說話者；AliMeeting 的 wav 是 WAVE_FORMAT_EXTENSIBLE，Python 內建 `wave` 讀不了，改成自己解析；Common Voice 是 mp3，用 soundfile 解碼、soxr 轉成 16 kHz。
6. 一開始把資料集放在 `C:\code\datasets`，依使用者要求搬到專案裡的 `datasets/`，並加進 `.gitignore`。

**模型選擇**（ADR-011，數字來源：[benchmark.md](../benchmark.md)）
- 比較了 11 組設定：X-ASR 160 ms／480 ms、k2 雙語 2023；VAD 門檻 0.5／0.65、斷句 0.3／0.4 秒、不用 VAD 斷句；CAM++／ERes2Net；分群門檻 0.35–0.65。
- 結果：X-ASR 160 ms 中文錯字率 1.4–1.7%、首次出字 0.83 秒；VAD 0.65 在噪音中說話者正確率 98.0%（0.5 時是 94.0%）；k2 雙語 2023 錯字率 5.6–7.0%。

### 真實語音、噪音、Whisper 與雲端 API 測試

**真實語音（[benchmark-real.md](../benchmark-real.md)）**
- 台灣腔：Common Voice zh-TW 11.7%、YouTube CC 對談 13.6%、台大課程 13.7%。大陸腔對照：AISHELL-1 4.0%；AliMeeting 遠距多人會議 45%。同樣是朗讀，台灣腔錯字率約是大陸腔的 3 倍。
- 常見錯誤：台灣地名和用語（捷運→潔運、三多→山多、石門→十門）、課程英文術語（self-supervised→Sales supervised、BERT→bird）。
- **問題：** 朗讀語料每句前後有 0.5–1 秒靜音，讓延遲算錯（一度顯示首次出字 1.85 秒、句尾負值）。**解法：** 把每句的起訖時間對齊到實際有聲音的地方，再重跑。修正後首次出字約 1.0 秒、句尾約 0.7 秒。
- **問題：** YouTube 字幕的時間是編輯過的，不是說話的時間。**解法：** 這組不報延遲。
- **問題：** 真實對談幾乎不停頓時，一行字幕會變得很長（句尾 p90 約 10 秒），而且同一人被拆成好幾個說話者。**解法：** 一行超過 8 秒後，只要 0.15 秒的換氣就斷行；少於 1.5 秒的短句不建立新的說話者。後者讓 AliMeeting 找到的說話者數從 6.5 降到 3.4（實際 3.1），但 Common Voice（句子很短）的說話者正確率從 94% 掉到 84%。門檻還在用 0.6／1.0／1.5 秒比較中。
- AliMeeting 多人重疊：重疊比例低的會議錯字率 10–13%，重疊多的 30–78%。

**噪音（[benchmark-noise.md](../benchmark-noise.md)）**
- 真實噪音（DEMAND 餐廳、街道、廚房、咖啡廳＋房間殘響，多人交談背景，電視＝人聲＋音樂），SNR 20 到 -5 dB，227 個檔。
- 字幕可用（錯字率 < 15%）的最低 SNR：廚房 -5 dB、街道 0 dB、餐廳 10 dB；多人交談背景、電視、殘響咖啡廳在 20 dB 就超過 15%。
- 純噪音 3 分鐘：電視 43 行假字幕、多人交談背景 40 行零碎字；音樂、街道、餐廳 0–1 行。
- 降噪模型：見 ADR-014，預設關閉。

**Whisper（你的 RTX 4070）與雲端 API（[benchmark-engines.md](../benchmark-engines.md)）**
- 使用者決定：自架模型只用自己的電腦，不租雲端 GPU；雲端只測 Google 和 Azure 的辨識服務（ADR-015）。
- GCP：帳單帳戶原本是關閉的，使用者開了新帳戶後，把專案連過去；設定 NT$320 預算快訊，以及 Speech API 每日 5 小時配額。Chirp 3 的台灣中文只在美國區提供（亞洲區已停止）。總花費約 US$1.30。
- Azure：使用者註冊免費試用，建立 Speech F0（East Asia）。第一次建立金鑰檔的 PowerShell 指令在新版 PowerShell 會寫入空值，改用 `NetworkCredential` 的寫法後正常。
- 結果摘要見 ADR-015。

## iPhone 版第一步

- 使用者想要 iPhone 版，選擇免費 Apple ID＋Mac 上的 Xcode，用線安裝（每 7 天重新簽），和 Android 版放在同一個 repo（ADR-017）。
- `:core` 改成 Kotlin Multiplatform。原本唯一用到 JVM 的地方是 `Char.isCjk()`（`Character.UnicodeBlock`），改成相同範圍的字碼區間。iOS 目標只在 macOS 上加入，Windows／Linux 和 Android 建置不受影響；`./gradlew :core:test` 照舊可用（改成跑 JVM 測試）。
- **問題：** opencc4j 是 JVM 函式庫，iPhone 不能用。**解法：** 在 `:core` 寫共用的 OpenCC 轉換器，讀同一批字典（ADR-018）。第一版照 OpenCC 原本的順序（先 ST 再 TW）結果完全沒有台灣用語；原因是 opencc4j 附的 TW 字典鍵是簡體，要放在最前面。修正後 15 句測試句和 opencc4j 完全相同。
- **問題：** sherpa-onnx 2.x 不再在版本 tag 下放 iOS 檔案。**解法：** 從它的 CI 設定找到新位置：`releases/download/xcframework/sherpa-onnx-v2.0.3-ios-static.xcframework.zip`，onnxruntime 要另外下載（1.28.2）。
- iOS 沒有內建 tar.bz2 解壓縮：用 SDK 的 libbz2 加一個小的 tar 讀取器（支援 GNU 長檔名與 pax），只解出需要的 4 個檔。
- GitHub Actions 新增 macOS 工作：核心在 iOS 模擬器上的測試、真機（未簽章）建置，以及模擬器上用真模型跑模型內附錄音的端對端測試。

### 下一階段 ④：延遲加速

- 新增 `:desktop --latency-breakdown`，把「開口到第一個字」和「說完到定稿」拆開量，並測各種設定（結果見 `docs/latency.md`，報告附圖表）。
- 發現：第一個字約 0.95 秒，大部分是模型（約 0.6 秒）和說話本身（約 0.25 秒）；電腦上的運算只有約 0.01 秒。定稿約 0.6 秒，主要是等 0.4 秒靜音確認說完。
- **問題：** 改成每 20 毫秒送一次聲音後，定稿看起來快很多，但其實是人聲偵測（Silero VAD，一次要 512 個取樣）在還沒收滿一個分析窗時回報「沒聲音」，讓句子提早結束。**解法：** 沒收滿就沿用上一次的判斷；桌面和 App 一起修，數字重跑。
- 採用 20 毫秒送聲音＋4 核心（ADR-021）：第一個字 0.95 → 0.91 秒、定稿 0.64 → 0.59 秒，錯字率不變。
- 熱詞（台灣用語詞表 `testdata/hotwords/taiwan.txt`，127 個詞）：單檔測試沒有改善，完整測試待做。

### 下一階段 ⑤：背景過濾與認聲音

- **背景過濾（音量）：** `FocusTracker` 把比最近主要說話聲小 8 dB 以上的句子當成背景。測試（`docs/benchmark-focus.md`）：電視 20 dB 時錯字率 69% → 50%，但乾淨對話會誤藏真的句子（6% → 12–15%），而且只有電視雜訊時的假字幕一句都沒少。所以預設關閉（ADR-020）。畫面上有「背景過濾：關／淡化／隱藏」按鈕。
- **認聲音：** 使用者長按一句字幕，輸入「這句話是誰說的」，App 用那句話的聲音特徵（CAM++）記住這個人（`VoiceRegistry`，相似度 ≥ 0.5 算同一人），之後自動顯示名字。聲音特徵只存在手機上。「認得的人」清單可以忘記某個人。有認得的人之後，不認得的聲音會被當成背景，並自動把背景過濾從「關」改成「淡化」（ADR-022）。
- 測試（`docs/benchmark-voices.md`，每位說話者用第一句登記）：只有電視聲的 3 分鐘裡，假字幕從 43 句降到 2 句，人聲嘈雜從 38 降到 1；電視 0 dB 時錯字率 122% → 80%。代價是乾淨對話會藏掉一些真的句子（8% → 12%），所以預設用「淡化」而不是「隱藏」，內容不會不見。

### iPhone：接行與 App 圖示（2026-11-28）

- 使用者實測回饋：同一個人說話時句子切得很碎、有些錯字、說話者容易混。先做最直接的一項：同一人短停頓（1.5 秒內）接在同一行（ADR-024）。錯字和說話者的部分之後用「整段重新辨識、重新分人」處理。
- App 圖示：黃色對話框裡一個黑色「字」，深色背景（`docs/assets/app-icon.png`，iPhone 的 `Assets.xcassets/AppIcon`）。iOS 圖示不能有透明，所以存成 RGB。

### iPhone：AI 校稿修正與雲端用量（2026-11-28）

- 實測回饋「AI 校稿會自己取消，關掉後紅字一直在底下」。原因：新字幕會取消上一輪校稿，連送出中的請求也取消，被當成失敗而暫停；錯誤訊息放在紅色錯誤行，只有按開始才清。修法見 ADR-026 的更新。
- 新增「雲端用量與費用」畫面（ADR-028）：Azure 收音時間、Claude 次數與 token、估計費用、Azure 免費額度進度，單價可改。
- 雲端用量畫面依使用者意見調整：不跳 Azure 免費額度提醒，改在每個服務底下寫計費標準（Azure 即時轉錄加說話者標籤約每小時 1.30 美元，免費方案每月前 5 小時免費；Claude 每百萬 token 單價）和目前估計費用。
- 新增逐字稿紀錄（ADR-029）：自動保存、搜尋、改標題、刪除，匯出 .txt／.srt。
- 新增雲端用量上限（ADR-030）：超過時提醒，這次改用離線，可選繼續用雲端。
- 字幕畫面深色／淺色跟隨系統，也可以手動固定（ADR-031）。
- 看電視模式（ADR-032）：最新幾句放大置中、不標說話者。
- 說話者辨識開關（ADR-033）。
- iPhone 認聲音：長按命名、認得的人頁（改名、合併、忘記），逐字稿裡整份改說話者名字（ADR-034）。
- iPhone 背景過濾（關／淡化／隱藏）與模型移除（ADR-035）。

### iPhone：看電視模式可以捲動（2026-11-28）

- 回饋「看電視模式無法滑動視窗」：改成整場字幕可往上滑回看；往上滑時不再自動拉回，「最新」按鈕或滑回最底恢復跟隨（兩種模式都一樣，ADR-032 更新）。
