# 技術決策紀錄（ADR）

每一條記錄：背景、決定、考慮過的其他選項、後果。編號只增不減。

---

## ADR-001 原生 Android（Kotlin + Jetpack Compose）

- **日期：** 2026-11-27
- **背景：** 先做 Android，需要低延遲地取得麥克風音訊並使用系統語音服務。
- **決定：** 用 Kotlin 和 Jetpack Compose 寫原生 App。
- **其他選項：** Flutter、React Native。這兩個需要額外的音訊與原生橋接層，延遲和除錯成本比較高。
- **後果：** 之後若要做 iOS 需要另寫畫面，但核心模組可以共用（見 ADR-002）。

## ADR-002 核心模組與畫面分離（`:core` 純 Kotlin）

- **日期：** 2026-11-27
- **背景：** 未來可能移植到智慧眼鏡；也需要在電腦上自動測試辨識流程。
- **決定：** 把 `SpeechEngine` 介面、`CaptionAssembler`、`TextProcessor` 放在不依賴 Android 的 `:core` 模組。
- **後果：** 同一套邏輯可以在 Android、桌面測試工具（`:desktop`）和其他裝置上使用，也能用 JVM 單元測試。

## ADR-003 第一個引擎用手機內建的語音辨識

- **日期：** 2026-11-27
- **背景：** 要盡快有可以跑的版本。
- **決定：** 先用 Android `SpeechRecognizer`（連線／離線兩種模式），每句結束後自動重新開始聆聽。
- **後果：** 很快能動，但無法分辨說話者、無法先降噪，句與句之間有短暫空檔。之後改為備用引擎（見 ADR-005）。

## ADR-004 「已確定」與「可能還會變」的字分開顯示

- **日期：** 2026-11-27
- **背景：** 即時辨識的中間結果會一直變動，對閱讀字幕的人很干擾。
- **決定：** 比對前後兩次中間結果的共同開頭，穩定的部分顯示黃色、可能變動的部分顯示灰色；定稿後變白色。
- **後果：** 讀者知道哪些字可以信任，閃動感降低，而且不增加延遲。

## ADR-005 需要分辨說話者，改為自己處理麥克風音訊

- **日期：** 2026-11-27
- **背景：** 使用環境吵雜、多人說話，需要標出不同的人。系統內建辨識不提供這些功能。
- **決定：** App 自己接麥克風：降噪 → 人聲偵測 → 語音辨識，同時抽取聲紋並分群成 A、B、C。
- **後果：** 主要引擎改用 sherpa-onnx（見 ADR-006）；系統內建辨識保留作為備用。

## ADR-006 離線引擎用 sherpa-onnx

- **日期：** 2026-11-27
- **背景：** 需要在手機上離線執行串流辨識、人聲偵測、聲紋。
- **決定：** 使用 sherpa-onnx（Apache-2.0），有 Android 版和中英雙語串流模型。
- **其他選項：** Vosk（中文品質較差、無聲紋）、whisper.cpp（非串流，延遲高）。
- **後果：** 第一次使用需下載約 165 MB 模型。模型選擇與參數由 benchmark 決定（見 ADR-009）。

## ADR-007 台語與高品質連線辨識改用自架伺服器

- **日期：** 2026-11-27
- **背景：** 台語辨識模型（Taiwan Tongues ASR、BreezeASR-Taigi）都是 Whisper 等級的大模型，手機跑不動。
- **決定：** 之後做一個 Docker 化、可放在任何雲端的 WebSocket 串流辨識伺服器（以 faster-whisper 或台灣調校過的模型為基礎），先在本機 RTX 4070 上測。
- **後果：** 連線模式會有伺服器費用；用量少時可以只在需要時開機。

## ADR-008 沒有實體手機時的測試方式

- **日期：** 2026-11-27
- **背景：** 目前手上沒有 Android 手機；Windows 模擬器拿不到某些電腦麥克風，模擬器也沒有中文離線語音包。
- **決定：** (1) 在 `:desktop` 用音檔跑完整辨識流程並量化；(2) App 的 debug 版加「播放 wav 當麥克風」模式，在模擬器上自動驗證；(3) 模擬器的麥克風改用 AirPods 可以收音，只用來做人工抽測。
- **後果：** 不需要真人說話也能重複測試；最後仍需要用實體手機和真人聲音驗證。

## ADR-009 以台灣口音的測試結果為主要依據

- **日期：** 2026-11-27
- **背景：** 使用者是台灣口音；常見開源測資（AISHELL、AliMeeting）和多數開源模型都偏中國口音。
- **決定：** 選模型和調參數以台灣口音測資（Common Voice zh-TW、台灣中文合成語音、台灣影片與課程）為準，中國口音只當對照；輸出一律用 OpenCC 台灣用語轉換。
- **後果：** 報告中兩種口音分開列；若台灣口音明顯較差，優先評估台灣調校過的模型。

## ADR-010 PR 在 CI 通過後自動合併

- **日期：** 2026-11-27
- **決定：** 使用合併提交（merge commit），CI 綠燈就合併到 main，不需人工按合併。
- **後果：** 進度不會卡在等待合併；每個 PR 仍要有清楚說明，方便事後回顧。

## ADR-011 離線引擎的模型組合：X-ASR 160 ms + Silero VAD 0.65 + CAM++

- **日期：** 2026-11-27
- **背景：** 第 2 步要選串流辨識模型、人聲偵測參數和聲紋模型，優先順序是速度，其次品質。
- **決定：** 語音辨識用 X-ASR zh-en 160 ms（int8，134 MB，約 100 萬小時中英語料訓練，含標點）。人聲偵測用 Silero VAD，門檻 0.65，說話停 0.4 秒後就結束這一行。說話者用 3D-Speaker CAM++ zh-en（28 MB），餘弦相似度門檻 0.5。
- **依據（TTS 測資，[benchmark.md](benchmark.md)）：** 中文錯字率 1.4–1.7%（乾淨到 5 dB 噪音），首次出字 0.83 秒（p50），噪音中說話者標籤 98.0% 正確。
- **其他選項：**
  - X-ASR 480 ms（第二名）：準確度相同、運算較省，但首次出字慢約 0.1 秒（p90 1.21 秒 vs 0.94 秒）。如果手機跑 160 ms 太吃力，可以改用它。
  - k2 zipformer 中英雙語 2023（淘汰）：錯字率 5.6–7.0%，是 X-ASR 的 3–4 倍，而且沒有標點。
  - VAD 門檻 0.5：乾淨語音一樣好，但噪音中說話者正確率只有 94.0%。
  - 不用 VAD 斷句、只靠辨識模型自己的規則：兩人的話會黏成一行，說話者正確率掉到 52–59%。
  - ERes2Net 聲紋：準確度和 CAM++ 相同，但比較大（40 MB）、不含英文訓練資料。
  - 分群門檻 0.35–0.45 會把不同的人合併；0.65 會把同一人拆開。
- **後果：** 所有候選模型都不是用台灣口音訓練的；台灣口音真實語音的結果見 benchmark-real.md，若明顯較差，再評估台灣調校模型（見 ADR-007、ADR-009）。

## ADR-012 離線模型在第一次使用時下載

- **日期：** 2026-11-27
- **背景：** 辨識、人聲偵測、聲紋和降噪模型合計約 165 MB；把它們包進 APK 會讓下載和更新都變慢，而且只用連線模式的人用不到。
- **決定：** 第一次選「離線＋說話者」並按開始時，從 sherpa-onnx 的 GitHub releases 下載到 App 內部儲存空間，顯示進度，每個檔案都檢查 SHA-256；辨識模型的壓縮檔只解出需要的四個檔。sherpa-onnx 的 Android 函式庫（AAR）在編譯時由 Gradle 下載並檢查 SHA-256，所以 GitHub Actions 也能編譯。
- **其他選項：** 包進 APK（APK 會變成 250 MB 以上）；用 Play Asset Delivery（要先上架 Google Play）。
- **後果：** 第一次使用需要網路；之後完全離線。下載中可以按按鈕取消。上架 Google Play 後可以再改成 Play Asset Delivery。

## ADR-013 斷句用人聲偵測，不只靠辨識模型

- **日期：** 2026-11-27
- **背景：** 對話中換人時，停頓常常只有 0.6 秒左右；辨識模型自己的斷句規則要等 0.8 秒以上的靜音，結果兩個人的話被放在同一行、同一個說話者標籤下。
- **決定：** 用 Silero VAD 每 32 毫秒的原始機率自己計算靜音：靜音達 0.4 秒、而且辨識文字 0.2 秒沒有變化時結束這一行；結束前補 0.4 秒靜音給辨識模型，讓它把還沒輸出的字吐出來。
- **其他選項：** 用 Silero 內建的分段（開始說話時要等 0.25 秒才判定，會把下一句的開頭切掉，英文會切在字中間）。
- **後果：** 說話者正確率約 98%，句尾定稿約 0.6 秒。在很吵的地方 VAD 可能一直以為有人在說話，這時會退回辨識模型自己的斷句（噪音驗證見 benchmark-noise.md）。

## ADR-014 降噪模型預設關閉

- **日期：** 2026-11-27
- **背景：** 要不要在辨識前先用 sherpa-onnx 的語音增強模型（GTCRN 0.5 MB、DPDFNet-2 10 MB）去除噪音。
- **依據（[benchmark-noise.md](benchmark-noise.md)，台灣腔，6 種真實噪音 × SNR 20 到 -5 dB）：** 兩個降噪模型都沒有讓錯字率下降，大多反而變差（例如餐廳 0 dB：39% → GTCRN 68%）。辨識模型本來就是用含噪音的資料訓練的，降噪造成的失真反而干擾辨識。降噪對說話者標籤有些幫助（餐廳 0 dB：57% → 74–82%）。GTCRN 的運算量是 0.09 RTF，DPDFNet-2 是 0.24。
- **決定：** 預設關閉；App 保留 GTCRN 選項（`SherpaOnnxEngine.DENOISER_DEFAULT = false`），模型很小，跟著一起下載。
- **後果：** 之後可以試「只把降噪後的聲音給說話者模型、辨識仍用原音」。最大的問題（背景有人說話、電視）要靠「只顯示近處主要說話者」的過濾來解決。

## ADR-015 伺服器與雲端引擎的方向

- **日期：** 2026-11-27
- **背景：** 比較手機 X-ASR、自架 GPU（Breeze-ASR-25、Whisper large-v3、turbo）、雲端 API（Google Chirp 3、Google V1、Azure）在台灣腔上的表現，見 [benchmark-engines.md](benchmark-engines.md)。使用者決定自架模型只用自己的電腦（RTX 4070），不租雲端 GPU；雲端只測 Google 和 Azure 的辨識服務。
- **結果：** Common Voice zh-TW 錯字率：Azure 5.1%、Chirp 3 8.0%、手機 X-ASR 11.7%、Breeze 12.9%（串流）／8.8%（離線）、Google V1 21.1%。首次出字：Google V1 0.6 秒、X-ASR 1.0 秒、Breeze 1.2 秒、Azure 1.3 秒、Chirp 3 3.7 秒。台大課程：Breeze 4.9%、X-ASR 13.7%。噪音和背景人聲時，所有引擎都很差。
- **決定：**
  1. 手機預設維持 X-ASR（最快出字、離線、免費、有說話者標籤）。
  2. 付費雲端選項優先做 Azure（最準、說話者標籤 97%、延遲和手機差不多）。Chirp 3 太慢、Google V1 不準，暫不放進 App。
  3. 自架伺服器（4070）用 Breeze-ASR-25，適合課程、演講等長時間、安靜的場合；它沒有說話者標籤，需要約 7 GB VRAM。turbo（3.7 GB）作為較輕的選項。
- **後果：** 下一步做引擎清單（含副標題、只下載需要的模型、可卸載），以及「只顯示近處主要說話者」的過濾。

## ADR-016 短句要多長才可以建立新的說話者：1.0 秒

- **日期：** 2026-11-27
- **背景：** 真實對談中同一個人常被拆成好幾個說話者，原因是很短的句子聲紋不準。加了「短句不能建立新的說話者」的規則，但門檻太高時，台灣腔朗讀（句子很短）的第二個人會被併到第一個人。
- **依據（`:desktop --sweep-new-speaker`）：**

  | 門檻 | Common Voice zh-TW 說話者正確率 | 找到／實際人數 | AliMeeting 說話者正確率 | 找到／實際人數 |
  |---|---|---|---|---|
  | 0.6 秒（等於沒有規則） | 93.8% | 2.4／2.0 | 52.2% | 6.3／3.1 |
  | **1.0 秒** | **93.4%** | 2.4／2.0 | 52.5% | 4.8／3.1 |
  | 1.5 秒 | 86.8% | 2.1／2.0 | 53.2% | 3.5／3.1 |

- **決定：** 用 1.0 秒。依 ADR-009 以台灣口音為主：1.0 秒幾乎不影響台灣腔朗讀的正確率，又讓會議中多出來的假說話者從 6.3 降到 4.8。
- **後果：** 會議中仍會多找出 1–2 個說話者；之後可以加「事後合併很像的說話者」。

## ADR-017 iPhone 版：同一個 repo，Kotlin Multiplatform 共用核心，SwiftUI 畫面

- **日期：** 2026-11-27
- **背景：** 使用者想要 iPhone 版，並問是否要跟 Android 版分開。`:core`（字幕組句、文字整理、說話者分群、串流管線）原本就是純 Kotlin，沒有用到 Android。
- **決定：**
  1. 同一個 repo。`:core` 改成 Kotlin Multiplatform：JVM 目標給 Android 和 `:desktop`，iOS 目標（iosArm64、iosSimulatorArm64、iosX64）打包成 `CaptionsCore.xcframework`。iOS 目標只在 macOS 上加入，所以 Windows、Linux 和 Android CI 的建置完全不變。
  2. iPhone 畫面用 SwiftUI（`ios/`），Xcode 專案用 XcodeGen 從 `ios/project.yml` 產生，不把 .xcodeproj 放進 repo。
  3. 離線引擎和 Android 一樣：sherpa-onnx 2.0.3（iOS 靜態 xcframework＋onnxruntime 1.28.2）、X-ASR 160 ms、Silero VAD、CAM++，同一組模型與 SHA-256，第一次使用時下載（ADR-012）。sherpa-onnx 的 Swift 包裝實作核心的 `StreamingAsr`、`VoiceActivityDetector`、`SpeakerEmbedder` 介面，斷句和說話者邏輯全部用共用的 `StreamingPipeline`。
  4. 安裝方式（使用者選的）：免費 Apple ID＋Mac 上的 Xcode，用線接 iPhone 安裝，每 7 天要重新簽一次；暫不付費、不用 TestFlight。
  5. GitHub Actions 的 macOS runner（`.github/workflows/ios.yml`）負責：核心在 iOS 模擬器上的測試、真機（未簽章）建置、模擬器上的 App 測試，包含用真模型跑錄音的端對端測試。這樣在使用者的 Mac 裝 Xcode 之前，就能確認程式可以編譯、模型可以跑。
- **其他選項：** 分開的 iOS repo 全部用 Swift 重寫（邏輯會分岔，兩邊結果不一致）；Compose Multiplatform 共用畫面（iOS 版還不夠成熟，也較難用 iOS 原生的音訊與無障礙功能）；Flutter／React Native（要重寫 Android 版）。
- **差異：** sherpa-onnx 的 C API 只提供 VAD 的「是否在說話」狀態，沒有 Android JNI 的逐格機率，所以 iOS 用最短靜音 0.1 秒的狀態代替，斷句可能比 Android 晚約 0.1 秒。實機測試時再比較。
- **後果：** 修改 `:core` 會同時影響兩個平台；兩個 CI（Build、iOS）都要通過才合併。

## ADR-018 簡轉繁台灣用語改成共用的 Kotlin 實作

- **日期：** 2026-11-27
- **背景：** Android 用 opencc4j（JVM 函式庫）把 sherpa-onnx 的簡體輸出轉成台灣繁體用語，iOS 沒辦法用。
- **決定：** 在 `:core` 加 `OpenCcTaiwanConverter`：讀 opencc4j 內附的同一批 OpenCC 字典（TWPhrases、TWVariants、STPhrases、STCharacters），最長詞優先轉換，再修正台灣異體字（啓→啟）。iOS 從 App 內附的字典檔建立轉換器（`ios/scripts/fetch-deps.sh` 從 Maven 取同一版 opencc4j 的字典）。JVM 測試在 15 句常見句子上和 opencc4j 比對，結果完全相同（軟件→軟體、視頻→影片、出租車→計程車、打印機→印表機、筆記本電腦→膝上型電腦、網絡→網路）。
- **其他選項：** iOS 內建 `Hans-Hant` 轉換（只有字，沒有台灣用語）；SwiftyOpenCC（多一個 C++ 套件要編譯）。
- **後果：** Android 暫時維持 opencc4j，之後可以改用同一個共用轉換器，少一個依賴。
## ADR-019 雲端金鑰由使用者自備，加密存在手機

- **日期：** 2026-11-27
- **背景：** 使用者要能自己設定 API 金鑰使用雲端引擎（Azure）。
- **決定：** 不經過我們的伺服器，App 直接用使用者的金鑰連 Azure。金鑰用 Android Keystore 的 AES-GCM 金鑰加密後存在 SharedPreferences，只顯示末 4 碼，可刪除。測試連線只要求存取權杖，不送音訊、不產生費用。關閉 Azure 的不雅字過濾。
- **其他選項：** EncryptedSharedPreferences（androidx.security-crypto 已停止維護）；由我們的伺服器代管金鑰（需要帳號系統，且金鑰集中存放風險高）。
- **後果：** 費用由使用者自己的 Azure 帳號支付；畫面顯示本次使用時間提醒。Google 雲端暫不提供（Chirp 3 太慢、V1 不準）。

## ADR-020 音量背景過濾預設關閉

- **日期：** 2026-11-27
- **背景：** 想把電視、隔壁桌等背景人聲從字幕中拿掉。第一版用音量判斷：比最近主要說話聲小 8 dB 以上就算背景。
- **決定：** 保留功能，但預設「關」；使用者可切換「淡化」或「隱藏」。
- **理由：** 乾淨對話時會誤藏真的句子（錯字率 6% → 12–15%），只有背景雜訊時假字幕完全沒減少（`docs/benchmark-focus.md`）。
- **後果：** 真正有效的背景過濾改用認聲音（ADR-022）。

## ADR-021 延遲設定：每 20 毫秒送聲音、4 核心，定稿靜音維持 0.4 秒

- **日期：** 2026-11-27
- **背景：** 使用者要求加速並說明延遲來源。實測見 `docs/latency.md`。
- **決定：** 聲音區塊從 100 毫秒改成 20 毫秒，辨識改用 4 核心；定稿前的靜音維持 0.4 秒；預設模型維持 X-ASR 160 ms。
- **理由：** 第一個字快 0.04 秒、定稿快 0.05 秒，錯字率不變。靜音改 0.3 秒定稿可再快 0.1 秒，但錯字率 10% → 11%，吵雜時也比較容易斷句；480 ms 模型慢 0.18 秒。
- **後果：** 再明顯變快需要延遲更低的模型；手機運算較慢，效果要在實體手機確認。

## ADR-022 認聲音：使用者指定名字，不認得的聲音當背景

- **日期：** 2026-11-27
- **背景：** 音量過濾不可靠（ADR-020），使用者同意「認聲音」：讓 App 認得身邊的人。
- **決定：** 長按字幕指定說話者名字，用該句的 CAM++ 聲音特徵登記（同名會合併，相似度 ≥ 0.5 算同一人）。有登記的人之後，不符合任何人的句子當成背景；第一次登記時，背景過濾若是「關」會自動改成「淡化」。聲音特徵只存在手機，可在「認得的人」清單忘記。
- **理由：** 只有電視雜訊時假字幕 43 → 2 句、人聲嘈雜 38 → 1 句（`docs/benchmark-voices.md`）。乾淨對話會誤判部分真句子（8% → 12%），所以預設淡化不隱藏。
- **其他選項：** 只用音量（ADR-020）；自動把第一個說話者當主人（家人輪流說話時會錯）。
- **後果：** 沒登記任何人時行為和以前一樣。
